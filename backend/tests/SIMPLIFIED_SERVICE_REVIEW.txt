Implemented locally
-------------------
The normal together.html route offers joining and creating immediately beneath
its Arabic introduction. No account, email, phone, surname or production tester
credential. The first join asks for a first name and explains that names and
participation will be publicly visible. Creation has first name, prayer, separate
Berlin date/time, optional note and a first-use consent checkbox. Subsequent
participation uses the remembered first name. Changing it applies to later joins
and creations; it does not silently rewrite other existing participation records.
An organizer is automatically participant one. Multiple same-prayer gatherings
are independent. Cards show first names, count and note; names use isolated bidi
text, never innerHTML. Join toggles to leave; only the organizer sees cancellation.

Network reads refresh on visibility/online events and every 30 seconds while
visible. A successful mutation immediately refreshes that browser; another
visible browser normally updates on its next poll. This is polling, not a live
subscription. Local expiry runs every second; server time anchors the display.
Offline actions are disabled, failed writes are not reported as confirmed, and
create retries reuse the operation ID. Server validation remains authoritative.

Privacy and security
--------------------
publicPrayerApi uses prayerService/public, separate from restricted staging's
prayerApi and prayerService/state. Legacy staging retains count-only prayer-v1
requests. Public named requests require prayer-v2, a first name of up to 40
Unicode characters, and an optional plain-text note of up to 120 characters.
HTML/control characters are rejected; no additional fields/profile data allowed.
The private random 32-byte browser capability travels only in Authorization, never
URLs; only hashes reach Firestore. Web Locks serialize first-use capability
creation across same-origin tabs; browsers without it reread the shared capability
before mutations (simultaneous first-use fallback is not guaranteed atomic). Quota hashes use a distinct rate: namespace and
cannot act as ownership keys. There is no Firebase Auth or public admin endpoint.

Leaving removes the stored first name immediately. Cancellation clears all names
and the note, retaining only a short-lived idempotency tombstone. At start time
the gathering becomes unavailable. Requests prune it, and authenticated hourly
cleanup deletes the entire record (names/note/ownership) within its next run.
Rate-limit records expire 26 hours after the last mutation, removed on subsequent
requests or the hourly cleanup, hence up to 27 hours when cleanup is operational.
No permanent attendance history or statistics. Cleanup failures can delay physical
deletion; they must be monitored, not described as impossible.

First name is remembered locally until changed or website data are cleared.
The local ownership capability expires after 26 hours without a mutation. Pending
create fields may persist locally until success or until their time passes on a
subsequent visit/request; clearing browser data also removes them. Clearing local
storage loses control of existing gatherings and does not cancel them remotely.
No names or note are sent merely by editing a form or changing the saved name.

Bounded public limits: 6 creations per browser/day, 24 global creations/day,
120 requests/minute and 10,000/day globally, 20 mutations/minute/capability,
24 live/tombstone records, 60 member/replay slots per gathering. Rate limits are
abuse/cost controls, not identity verification; new browsers can obtain new
capabilities. Direct Firestore access still denied. Public API remains disabled
by default, with empty allowed-origin configuration. No cloud changes were made.
Runtime instance limits, monitoring, staging credentials and private review files
were not changed. No MAWAQIT, logo or sermon workflow changes.
